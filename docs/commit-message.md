# Commit messages

Applies to every commit in this repo, whether a person or a coding agent writes it.

## Format

```text
<type>(<scope>)!: <description>

<body: what changed and why, wrapped at 72 characters>

<footers>
```

- `<type>` is required.  See [Types](#types).
- `(<scope>)` is optional.  See [Scopes](#scopes).
- `!` is used only for breaking changes.  See [Breaking changes](#breaking-changes).
- The body and footers are optional for trivial changes, but most commits should have a body.

### Template

```text
type(scope): summarize change in 50 characters or less

More detailed explanatory text if necessary. Wrap lines to about
72 characters. Focus on why you are making this change and what
problem it solves, rather than how you did it.

- Bullet points are fine too
- Use a hanging indent for multi-line bullets, so continuation
  lines line up with the text above them

Resolves: #123
```

## The 7 golden rules

1. Separate the subject from the body with a blank line.
2. Keep the subject line to 50 characters or less (72 max).  The limit includes the type and scope prefix.
3. Start the description after the `type(scope):` prefix in lowercase (`feat: add header banner`).  Capitalize the first word only in a subject without a prefix, such as a merge or revert generated by Git.
4. Do not end the subject line with a period.
5. Use the imperative mood ("add feature", not "added feature" or "adds feature").  A good subject completes the sentence: "If applied, this commit will _[description]_."
6. Wrap the body at 72 characters.
7. Explain what and why, not how.  The code shows how; the message records the context: the problem, the decision, and anything a reviewer or future reader would not see in the diff.

## Types

| Type | When to use it |
| --- | --- |
| `feat` | A new feature for the user |
| `fix` | A bug fix |
| `docs` | Documentation-only changes (`/docs`, `AGENTS.md`, READMEs, code comments) |
| `style` | Code formatting only: whitespace, semicolons, lint autofixes, with no behavior change.  **Not** SCSS / visual changes; those are `feat` or `fix`. |
| `refactor` | Restructuring production code without changing behavior (e.g., renaming, extracting a component) |
| `perf` | A code change that improves performance |
| `test` | Adding missing tests or correcting existing tests |
| `build` | Build system or dependency changes (Heft config, `package.json` dependencies, `package-lock.json`, SPFx upgrades) |
| `ci` | CI pipeline configuration |
| `chore` | Other maintenance that does not touch production code or the build (e.g., `.gitignore`, editor settings, provisioning scripts) |
| `revert` | Reverts an earlier commit.  The body names the reverted commit's hash and says why. |

If a commit fits more than one type, it is probably more than one commit.

## Scopes

Use the workspace or area that the change targets:

- an SPFx package folder name: `customizers-global`, `webparts-global`, `shared`
- `scripts` for provisioning scripts and configurations
- `docs` is not needed as a scope; use the `docs` type instead.

Leave the scope out when a change spans several areas.

## Breaking changes

Mark a breaking change with `!` after the type/scope **and** a `BREAKING CHANGE:` footer that says what consumers must do.  Examples in this repo:

- a changed or removed customizer / web part property, which requires updating `/scripts/config/*.json` or existing web part instances
- a renamed or removed export from `@kanduu/spfx-shared`
- a script parameter change.

## Body

- Say why the change was needed and what it does at a high level.
- For dependency changes, name the approval (who and when) and note the `/docs/dependencies.md` update.
- Mention anything deliberately left out or deferred ("search box is a stub; no search logic yet").

## Footers

- Issue links: `Refs: #12` (related), `Resolves: #12` / `Closes #12` (GitHub closes the issue when the commit reaches the default branch)
- `BREAKING CHANGE: <what changed and what to do>`
- Co-authors (including coding agents): `Co-Authored-By: Name <email>`

## Other guidelines

- One logical change per commit.  Formatting-only or refactor changes go in a separate commit from behavior changes.
- Every commit should build (`npm run build`).

## Pull requests and squash merges

A squash merge replaces the branch's commits with one commit whose subject is the PR title and whose body comes from the PR description.  So:

- Write the PR title as a commit subject that follows these rules: `type(scope)!: description`, imperative, no period.  Use the type of the most significant change, and include `!` if any commit in the PR is breaking.
- Keep any `BREAKING CHANGE:` footer in the PR description (or the squash dialog), so it reaches the default branch.
- Before confirming the squash, check GitHub's generated message.  It often lists every commit subject; replace that list with a body that explains what and why.

## Examples

```text
feat(customizers-global): add themed header banner

Replace the Yeoman sample alert with a React banner in the Top
placeholder, colored from the site theme via the SPFx ThemeProvider
service. Wrap it in a Fluent ThemeProvider so future menus, panels
and dialogs inherit the site theme.

The ticker, search box, settings and profile controls are stubs with
no behavior yet.
```

```text
build(customizers-global)!: provision with PnP.PowerShell, not XML

Feature XML fixes customizer properties inside the package, so every
site gets the same configuration, and it can register the header a
second time alongside the script. Remove the feature XML and add a
re-runnable script with per-site JSON configurations.

BREAKING CHANGE: deploying the .sppkg no longer activates the header.
Run scripts/Set-ApplicationCustomizer.ps1 on each site.
```
